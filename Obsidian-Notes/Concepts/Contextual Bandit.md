A **Contextual Bandit** is a [[Multi-Armed Bandit]] variant where each arm's expected reward is modeled as a function of side information ("context") available at decision time — rather than treating every round as identical and learning one belief per arm in isolation. Examples of the algorithm family: LinUCB, contextual Thompson Sampling.

**Why it's required — not optional — for [[Supply Brain]].** A plain bandit learns one belief per arm and nothing more. With 5,000 SKUs, running an independent bandit per SKU means each one only gets a trickle of rounds (roughly one replenishment cycle per week), which is far too sparse for beliefs to converge within the project timeline. Context solves this by letting the model generalize: SKUs that share relevant features can share what's been learned about them, instead of each SKU starting from zero.

**The context variable actually used here.** Rather than per-SKU context, the project pools bandits by **(segment × seasonal phase)** — see **[[SKU Segmentation]]** for how segments are defined, and **[[Non-Stationarity (Bandits)]]** for why seasonal phase specifically needs to be its own context dimension rather than folded into the segment label. This gives every SKU in "Seasonal-Beverages, peak phase" a shared, faster-converging belief, while still distinguishing "Seasonal-Beverages, trough phase" as a materially different decision context.

**The trade-off context introduces.** More context dimensions mean faster generalization but sparser data per context bucket — segment × seasonal phase was deliberately chosen as *enough* granularity to fix the seasonality problem without over-fragmenting the data. The worked design note in **[[Multi-Armed Bandits — Supply Brain Strategy]] §5** is explicit that Fast-Moving and Intermediate segments likely don't need the seasonal-phase split at all — a single belief per segment already works fine there, since seasonality barely moves demand for those segments.
