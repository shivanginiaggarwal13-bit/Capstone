# Supply Brain — Phase 2 SKU Segmentation (Final Approach)

This folder reads its data directly from your Capstone workspace's
`input datasets` folder — it does NOT keep its own copy of the dataset.
Place this `segmentation` folder as a SIBLING of `input datasets`:

```
Capstone/
├── input datasets/        <- your existing 14 raw dataset CSVs (unchanged)
├── segmentation/          <- this folder
│   ├── build_sku_clusters_final.py
│   ├── outputs/
│   └── README.md
└── ...
```

## What this does

Produces **two segmentation outputs**, as agreed with the team:

- **Output 1 — Annual**: one global k-means clustering across all 500 SKUs,
  using whole-year (2025) feature averages.
- **Output 2 — Quarterly**: the same approach, re-run fresh for each of
  2025's four quarters, so you can see whether/how a SKU's segment shifts
  across the year.

Neither output splits by category — clustering runs on the full catalog at
once. Elasticity (`elasticity_base`/`elasticity_promo`) is computed and kept
for reference/profiling, but deliberately excluded from the clustering math
itself (see "Methodology notes" below for why).

Both outputs include:
- A **business-friendly cluster name**, generated by rule (not manually
  guessed) from each cluster's own profile — e.g. "High-Revenue",
  "Long-Tail / Stockout-Risk".
- A **financial exposure estimate** — `stockout_exposure_usd = revenue ×
  stockout_rate × stockout_cost_multiplier` — so you can talk about dollars
  at risk, not just percentages.
- An **ANOVA F-test** per feature, confirming which differences between
  clusters are statistically real vs. noise.
- A **PCA 2D visualization** (PNG) of the clusters, for a slide.
- A **revenue/margin concentration profile** (% of catalog vs. % of revenue
  vs. % of margin per cluster).

| `sku_clusters_annual.csv` | One row per SKU: every feature, cluster id, cluster name |
| `cluster_business_profile_annual.csv` | Per cluster: SKU count, revenue %, margin %, stockout exposure $, cluster name |

## Methodology notes (read before presenting)

**Why elasticity is excluded from the clustering math.** Elasticity is
computed once per category (not per SKU — an earlier per-SKU attempt was
too unstable with limited price history per individual product), so it
only has 5 distinct values across the whole catalog. A feature with only
5 possible values dominates k-means distance calculations and effectively
turns the clustering into "which category is this," rather than finding
real cross-category behavior. Elasticity is still computed and kept in the
output for reference — just not fed into the clustering itself.

**Why cluster names are rule-based, not manual.** `name_clusters()` tags
each cluster using: (a) a **revenue-to-catalog-share ratio** — flagging
"High-Revenue" only when a cluster's revenue share is at least 2x its SKU
share, and "Long-Tail" only when it's 0.3x or less (this avoids mislabeling
a merely-average cluster as "Long-Tail" just for not being the single top
performer — an issue caught and fixed during testing); and (b) **z-scores**
across the cluster means for margin, stockout rate, demand volatility, and
lead time. This keeps naming reproducible and explainable if questioned.

**Why quarterly uses only 2025.** Real transaction/actuals data
(`orders.csv`, `demand_forecast.csv`'s `in_sample` rows, `inventory.csv`,
`production.csv`) only covers 2025 in full; 2026 exists only as a forward
forecast with no real actuals to validate against. So Output 2 shows
genuine **within-year** movement, but cannot yet confirm a **repeating**
year-over-year cycle — that would need at least one more year of real data.

**Structural vs. time-varying features in Output 2.** Price, shelf life,
and lead time don't vary by quarter in this dataset (no seasonal lead-time
or pricing model exists), so they're held static across all 4 quarters.
Demand volatility, forecast accuracy, revenue, realized margin, supply
variability, and stockout rate ARE recalculated fresh each quarter, using
only that quarter's ~13 weeks of data.

**Known gaps to check before presenting:**
- 9 SKUs have no resolvable lead-time path in the network data (a gap in
  the lane data, not a bug) — these get median-imputed.
- Elasticity R² is low (0.5%–4% depending on category) — directionally
  trustworthy (all negative, consistent with literature), but don't oversell
  precision if asked how confident the exact numbers are.
- `k` is auto-selected by silhouette score with a business floor (won't
  pick k=2 unless it wins by a wide margin) — always check the printed
  elbow/silhouette table before presenting a specific k as final.
